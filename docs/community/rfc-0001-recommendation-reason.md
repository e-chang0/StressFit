# RFC-0001: 추천 이유를 어떤 항목으로 보여줄까?

- 상태: 의견 수렴
- 작성일: 2026-11-03
- 의견 수렴 기한: 2026-11-10(한국 시간)
- 실제 토론: [Discussions #14](https://github.com/e-chang0/StressFit/discussions/14)
- 관련 자료: [ADR-0001](../adr/0001-rule-based-recommendation.md), [README](../../README.md)

## 배경

현재 추천 데모는 결과의 `reason` 문자열을 화면에 보여준다. 전체 서비스로 확장할 때 어떤 조건을 설명에 포함할지, API와 화면에서 어떻게 함께 관리할지는 아직 정하지 않았다. 설명이 너무 일반적이면 사용자가 자신이 입력한 조건이 반영됐는지 알기 어렵다.

## 제안

첫 버전은 실제 추천에 사용한 조건 중 시간, 장소·기구, 운동 경험을 짧은 문장으로 보여준다. 최대 두 문장으로 제한하고, 입력하지 않았거나 계산에 쓰지 않은 조건은 이유에 넣지 않는다.

예를 들어 '집 / 기구 없음 / 10분 / 초보'를 입력했고 그 조건으로 루틴을 골랐다면 다음과 같이 표시한다.

> 기구 없이 집에서 할 수 있는 10분 루틴입니다. 처음 운동하는 경우를 기준으로 골랐습니다.

백엔드는 추천 결과와 `reasonCodes` 목록을 같이 보내고, 화면은 코드에 맞는 설명을 보여주는 방식을 제안한다. 코드 이름은 예를 들어 `TIME_MATCH`, `NO_EQUIPMENT`, `BEGINNER`로 정할 수 있다. 이는 API 설계 제안이며 아직 구현되지 않았다.

스트레스가 얼마나 감소한다는 식의 효과 문구는 넣지 않는다. 이유는 입력 조건과 추천 과정에 대한 설명으로 한정한다.

## 다른 방법

| 방법 | 좋은 점 | 아쉬운 점 |
| --- | --- | --- |
| 모든 결과에 같은 한 문장 | 구현하기 쉽다 | 입력이 어떻게 반영됐는지 알 수 없다 |
| 추천 규칙 전체를 표시 | 확인할 정보가 많다 | 설명이 길고 내부 규칙이 화면에 그대로 나온다 |
| 조건별 짧은 문장 최대 두 개 | 읽기 쉽고 반영한 조건을 알 수 있다 | 표시할 조건의 우선순위를 정해야 한다 |

## 단점과 부담

이유 코드와 화면 문구를 함께 관리해야 한다. 추천 조건이 세 개 이상 일치하면 어떤 두 가지를 먼저 보여줄지도 정해야 한다. 일치한 조건이 없을 때는 없는 이유를 만들지 않고, 이유를 표시하지 않는 방안을 제안한다.

## 의견을 받고 싶은 점

1. 최대 두 문장이면 충분한가? 조건을 태그로 보여주는 편이 더 읽기 쉬운가?
2. 조건이 여러 개면 시간과 장소를 먼저 보여줘도 괜찮은가?
3. 이유 코드가 없는 결과는 설명을 생략할까, 입력 조건을 확인하라는 안내를 넣을까?

## 결정 기록

의견 수렴 중이다. 작성자의 제안이며 다른 참여자의 동의나 실제 사용성 평가 결과는 아직 없다. 기한 후 의견과 남은 문제를 정리하고, 결정되면 API와 화면 작업 이슈에 연결한다.
